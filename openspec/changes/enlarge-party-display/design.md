## Context

現状の `PartyDisplay` は画面下中央に固定幅の 3列×2行 (パネル 180×80) で配置されており、ダンジョンの中央視界(階段・敵)とエンカウンタダイアログに視覚的に干渉する。フォントは 14pt と小さく、HP/MP の値が読みづらい。

本変更は「パーティ表示の段階的強化」3部作の第1段で、レイアウトと文字サイズの再構成のみを扱う。後続の `persistent-party-display`(常駐化・状態異常アイコン・行動不能暗転)、`combat-party-reactions`(戦闘リアクション)へ繋ぐ土台を作る。

ダンジョンスクリーンショット(`tmp/dungeon2.png`)で確認した通り、画面下端は左右合わせて約 1280px 確保でき、中央 200px 程度を空けても 6 パネル(180×6 = 1080px)+左右マージンが収まる。

## Goals / Non-Goals

**Goals:**
- 1 行 6 パネル構成に再配置し、ダンジョン中央視界を確保する
- 前列を左下、後列を右下に配置し、ゲーム的な前後関係を視覚で示す
- "FRONT" / "BACK" ラベルで配置の意味を明示する
- フォントを 20pt に拡大、パネル高さは行間調整して名前/LV/HP/MP の 4 行が無理なく収まるサイズに整える
- 空スロットを完全に透明にして、編成途中のパーティでもクリーンに見せる
- 全体背景帯を廃止して視覚ノイズを下げる

**Non-Goals:**
- マウント先の追加(街等への展開は `persistent-party-display`)
- 状態異常・バフ/デバフのアイコン描画 (`persistent-party-display`)
- 行動不能(死亡・睡眠等)時の暗転表示 (`persistent-party-display`)
- 戦闘時のアニメーション(lift / shake / heal flash) (`combat-party-reactions`)
- combat 側のシグナル追加 (`combat-party-reactions`)
- トグル機能(常時表示で固定)
- 描画項目(名前/LV/HP/MP)の追加・変更

## Decisions

### D1. レイアウト戦略: 1 行 6 パネル、前列左詰め・後列右詰め
- 採用理由: ダンジョン中央視界(進行方向)を最優先で空けたい。前後列の意味を左右で表現することで、視線移動だけで前後列が認識できる。
- 代替案A (3列×2行 を全幅にスケール): 視界中央が常に塞がる。却下。
- 代替案B (1 行 6 パネルを左から並べる): 中央が塞がる + 後列の意味が不明瞭。却下。
- 代替案C (コンテナノード `HBoxContainer` + spacer): やってもよいが、現状コードが手動配置(`position` 直接指定)なのでそのスタイルを維持し、手動配置で実装する。

### D2. パネル幅とパネル高さ
- 採用: パネル幅 180 を維持。高さは 80 → 100〜110 の範囲で調整(4 行 × 行高 ≈ 24-26px + 余白)。
- 採用理由: パネル幅は現状で名前/LV/HP/MP が問題なく収まっていた。フォントを 14→20 に上げると行高が伸びるので高さだけ調整する。
- 具体値: `PANEL_HEIGHT = 110` を起点に、実装中にテスト/手動確認で調整可能とする。

### D3. フォントサイズ
- 採用: `FONT_SIZE = 20`(現状 14)。
- フォント本体は `ThemeDB.fallback_font` のまま(プロジェクト全体のフォント方針はスコープ外)。

### D4. FRONT / BACK ラベル
- 採用: ラベル描画は `PartyDisplay` 側の `_draw()` で行う(子 Control を増やさない)。位置は前列・後列パネル群の真上、左右の端揃え。
- フォントサイズ: 20pt 程度(本文と同等)。色: 白系。
- 代替案: `Label` ノードを子に追加。手動配置が崩れた時に追従しやすいが、現状の手動 position 配置と整合させるため `_draw()` で描画する方針を採る。

### D5. 全体背景帯(`_bg_panel`)の廃止
- 採用: `ColorRect` の `_bg_panel` は削除する。各 `PartyMemberPanel` が自身の `BG_COLOR = Color(0.15, 0.15, 0.2, 0.7)` を持っているため、パネル単位の半透明背景は維持される。
- 視覚的効果: 中央が完全に透明になり、ダンジョン視界とパーティ HUD が綺麗に分離される。

### D6. 空スロット = 完全透明
- 採用: `_data == null`(または `_character == null` でかつスナップショットも null)のとき、`PartyMemberPanel._draw()` は何も描画しない。背景矩形も含む。
- 現状動作: 現状は `_data == null` でも `BG_COLOR` の矩形は描かれ、その後で early return している。今回の変更で「null なら矩形すら描かない」に切り替える。
- スロット位置の予約: パネル位置は固定したまま(詰め直しはしない)。例えば前列が「F1=A, F2=null, F3=B」なら F2 のスロット位置は空けたまま F3 が右端に表示される。

### D7. PartyDisplay のアンカー
- 採用: `anchor_left = 0.0`, `anchor_right = 1.0`, `anchor_top = 1.0`, `anchor_bottom = 1.0`(画面下端を全幅で覆う)。
- 内部での前列/後列パネル配置は手動 `position` で左端・右端から margin オフセット。
- ラベルとパネルの上下位置: 上部にラベル領域(高さ ~24px)、下部にパネル領域(高さ ~110px)。HUD 全体高さは ~140px 強。

### D8. 既存 API の互換維持
- `PartyDisplay.setup(party_data)` / `bind_party_characters(front_row, back_row)`、および `PartyMemberPanel.bind_character` / `set_member` のシグネチャと挙動は変更しない。
- `DungeonScreen` 側のマウント・bind コードも変更しない(レイアウトは PartyDisplay が自分で決める)。

## Risks / Trade-offs

- **フォント 20pt がパネル幅 180 に収まらない名前がある可能性** → 名前は左寄せで draw_string、必要なら次変更で width パラメータを渡してクリップ。今回は実装後に手動確認で問題があれば値を微調整。
- **空スロットの背景矩形を描かない方針が、レイアウトデバッグ時に見えにくい** → デバッグ時のみ可視化する仕組みは入れない(YAGNI)。レイアウト不整合はテストで検出する。
- **画面解像度が想定より狭い場合(例 1024×768 等)、左右の 3 パネルが衝突する** → 現状のプロジェクト設定の解像度を前提にする。狭画面対応は別変更で。

## Migration Plan

- 単一コミットでレイアウトを切り替える。後方互換のレイアウト切替フラグは持たない。
- 既存テスト(`tests/dungeon_scene/test_party_display_character_binding.gd` 他)はレイアウト依存のアサーションがあれば新レイアウトに合わせて更新する。シグナル経路の検証はそのまま通るはず。

## Open Questions

- PANEL_HEIGHT の最終値(100 / 105 / 110)→ 実装フェーズで確定。
- FRONT/BACK ラベルの色味(純白 vs 薄い灰)→ 実装フェーズで手動確認して確定。

これらは実装中に決めても影響範囲が小さいので、design では選択肢を残す。
