## Context

`CellMeshBuilder` は 1 セル分の幾何を生成する RefCounted で、`DungeonScene._rebuild_mesh` から `visible_cells` の各セルに対して呼ばれている。各セルの 4 エッジ (NORTH/SOUTH/EAST/WEST) は `WizMap.set_edge` によって両側のセルに同時設定されており、現状の per-cell 描画では「同じ壁を 2 セルが両方クワッドとして出力する」状態。シェーダ側で `cull_disabled` のため Z-fighting は問題にならず、視覚的には単一クワッドのように見えている。

ジオメトリを box (厚さあり) にすると、この二重描画は Z-fighting と内側面の重複描画として顕在化するため、エッジ単位の重複排除が必須となる。同様に、コーナー柱は最大 4 セルに共有されるため、コーナー単位の重複排除も必要。

## Goals / Non-Goals

**Goals:**
- 壁を厚さ 0.20m の直方体として描画し、コーナーや交差部から見たときに「紙感」を排除する
- 壁が接するコーナーに柱を立て、壁端面の露出を意匠的に解決する
- 床・天井の接合部に幅木 / 笠木を入れて空間の輪郭を締める
- ドアを枠 (lintel + jamb) と凹んだドア板の建具構造として表現する
- 既存の procedural brick / wood-plank シェーダ表現を維持する
- 既存の探索・移動・ミニマップ等のロジックには一切影響を与えない

**Non-Goals:**
- シェーダ自体の改修 (ノーマルマップ、パララックス等) — 別変更で扱う
- アーチ型ドア枠 — シンプルな矩形枠で進める
- 動的なドア開閉アニメーション — 静的な凹みで表現
- 照明系の変更 (壁掛け松明、ちらつき等) — 別変更で扱う
- 物理コリジョンの変更 — 移動可能性は WizMap データのみで決まる

## Decisions

### Decision 1: per-batch リファクタによる重複排除 (壁オーナーシップ)

**選択**: `CellMeshBuilder.build_meshes(visible_cells: Array[Vector2i], wiz_map: WizMap) -> Array[Face]` を新設し、内部で「エッジ単位」「コーナー単位」のユニーク化を行う。

**代替案**:
- A2 (正準オーナ): 各セルが「自分の北・西エッジだけ」を描画する規約。境界セルや視野コーン端で対応セルが不在/不可視のときに穴が開く。視野ベースでの欠落リスクが高く却下。
- A3 (内側にリブだけ追加): 既存クワッドはそのままで内側に厚みリブを追加する。壁端面の問題は解決せず、コーナー柱の根拠も曖昧になる。却下。

**根拠**: per-batch 方式なら `visible_cells` セット情報を持って描画判定できるため、視野コーン端の欠落・重複どちらも一元的に処理できる。floor / ceiling / landmark はセル一意なので per-cell の処理を維持し、壁・柱・トリムだけを per-batch で扱う。

**互換性**: 旧 `build_faces(cell, pos)` は残し、内部実装を「ステージング配列に追加するだけ」のものに変更可能。だが今回は `DungeonScene` も同時に更新するので、`build_faces` は landmark・floor・ceiling 専用に縮小し、`build_meshes` から呼ぶ形に再構成する。

### Decision 2: 壁 box の寸法と頂点配置

**選択**: 厚さ T = 0.20m、高さ CELL_HEIGHT = 2.0m、長さ CELL_SIZE = 2.0m の直方体。エッジの「中心線」を壁の中心軸とし、左右に T/2 = 0.10m ずつ厚みを持たせる。

```
平面図 (北壁の例、北は -Z 方向):
    
    z = z0 - 0.10  ┃▓▓▓▓▓▓▓▓▓▓▓┃  ← 外側の面 (隣セル側)
    z = z0         ┃ 中心軸     ┃
    z = z0 + 0.10  ┃▓▓▓▓▓▓▓▓▓▓▓┃  ← 内側の面 (このセル側)
                   x0          x1
                   
Box の 6 face:
    - inner (このセル側、Z+ 法線)
    - outer (隣セル側、Z- 法線)
    - top   (天井側、Y+ 法線)
    - bottom (床側、Y- 法線)  ← 床ジオメトリで隠れるが描画する
    - east  (X+ 法線)         ← 通常は柱で隠れるが描画する
    - west  (X- 法線)
```

**代替案**:
- T = 0.10m: 細すぎてコーナーから見たときの厚み感が乏しい
- T = 0.40m: 通路の有効幅が 1.6m まで狭まり、視野が圧迫される

**根拠**: T = 0.20m は CELL_SIZE 2.0m に対して 10%。建築物として違和感のないプロポーション (一般的な間仕切り壁の比率) で、かつカメラがセル中心 (内側面から 0.90m) にあるので圧迫感は最小限。

### Decision 3: コーナー柱の判定ルール

**選択**: マップ上の各コーナー (i*CS, j*CS) について、その点に集まる最大 4 本のエッジ (上下左右) のうち、1 本でも `WALL` または `DOOR` ならその位置に柱を立てる。

**判定詳細**:
コーナー (i, j) に集まるエッジは:
- 西側エッジ: cell(i-1, j-1).south = cell(i-1, j).north
- 東側エッジ: cell(i, j-1).south = cell(i, j).north
- 北側エッジ: cell(i-1, j-1).east = cell(i, j-1).west
- 南側エッジ: cell(i-1, j).east = cell(i, j).west

それぞれ、参照セルが範囲外なら「WALL とみなす」(マップ境界は壁扱い)。`OPEN` 以外が 1 本でもあれば柱配置。

**代替案**:
- 「2 本以上 WALL」: 壁端 (1 本だけ WALL) で柱が立たないため、断面剥き出しになる。却下。
- 「全 4 本が WALL」: 十字交差にしか柱が立たず、T 字や直線壁の途中、壁端のいずれもカバーできない。却下。

**根拠**: 「壁に接するコーナーのみ」というユーザ要件をシンプルに満たす。広い部屋の中央セルはどのコーナーも 4 本全 OPEN なので柱は立たず、視界を遮らない。

### Decision 4: コーナー柱の寸法

**選択**: 0.25m 角 × CELL_HEIGHT (2.0m) の直方体。色は `WALL_COLOR` よりわずかに暗い `PILLAR_COLOR = Color(0.45, 0.43, 0.38, STONE_ALPHA)`。

**根拠**: 0.25m = 壁厚 0.20m + 周辺余裕 0.05m。壁の box から少しはみ出すサイズで「柱が壁端を抱きかかえる」見た目になる。色が壁と全く同じだと柱として識別しにくいので、わずかに暗くして陰影効果を上乗せ。

### Decision 5: 幅木 / 笠木の寸法

**選択**: 高さ 0.08m、壁面から内側に 0.04m 突出する細いリブ。色は `WALL_COLOR` の派生 (現時点では同色で十分、視認性は陰影とシェーダのレンガパターンで確保)。

```
側面図:
    
    ┃                              ← 壁本体 (box の inner 面)
    ┃▒▒▒  ← cornice (高さ 0.08m, 突出 0.04m)
    ┃     y = CELL_HEIGHT - 0.08
    ┃
    ┃
    ┃▒▒▒  ← skirting (高さ 0.08m, 突出 0.04m)
    ┃     y = 0.08
    ──────  ← 床
```

**ジオメトリ**: 各 WALL/DOOR エッジについて、内側面に沿った細い直方体を 1 本ずつ追加する。長さは CELL_SIZE。

### Decision 6: ドア建具構造

**選択**: DOOR エッジは以下 4 要素から構成される:

```
正面図 (高さ CELL_HEIGHT = 2.0m):
                                     
    ┌─────────────────────────┐  ← lintel (上枠)
    │█████████████████████████│      高さ 0.20m, 厚さ 0.20m (壁同等)
    ├──┬─────────────────────┬──┤
    │  │░░░░░░░░░░░░░░░░░░░░░│  │  ← jamb (左右枠)
    │左│░░░░░░░░░░░░░░░░░░░░░│右│      幅 0.18m, 厚さ 0.20m
    │枠│░░░░ door_panel ░░░░░│枠│
    │  │░░░░ (凹み 0.10m) ░░░│  │  ← door_panel (扉本体)
    │  │░░░░░░░░░░░░░░░░░░░░░│  │      高さ 1.80m, 幅 1.64m
    │  │░░░░░░░░░░░░░░░░░░░░░│  │      厚さ 0.04m, 中心軸から 0.10m 凹む
    └──┴─────────────────────┴──┘
                                     
寸法まとめ:
    CELL_SIZE = 2.0, CELL_HEIGHT = 2.0
    壁厚 T = 0.20
    lintel: 上端から 0.20m 下まで (y: 1.80 ~ 2.00)
    jamb:   各 0.18m 幅 (x: 0~0.18 と 1.82~2.00)
    door_panel: 残り (x: 0.18~1.82, y: 0~1.80)
                壁の中心軸 (z=z0) から開口側に 0.10m 凹む
```

**ジオメトリ要素**:
- `door_lintel_*`: 上枠 box (色は WALL_COLOR = 石)
- `door_jamb_left_*`: 左枠 box (色は WALL_COLOR)
- `door_jamb_right_*`: 右枠 box (色は WALL_COLOR)
- `door_panel_*`: 凹んだ扉本体 box (色は DOOR_COLOR = 木、シェーダのプランク模様が乗る)

**根拠**: lintel + jamb で「壁の開口部」を表現し、その奥に door_panel が見える形。凹みがあるので斜めから見ても建具として立体的に認識できる。プランク模様は既存の `WOOD_ALPHA` フラグで自動的に切り替わる。

### Decision 7: 既存テストの取り扱い

`test_cell_mesh_builder.gd` の以下テストは新ジオメトリで成立しなくなる:
- `test_wall_north_generates_quad`: 壁が単一クワッドである前提
- `test_wall_vertices_at_correct_position`: 単一クワッドの頂点位置を検証
- `test_door_generates_door_face`: door が `door_north` の単一クワッドである前提
- `test_all_four_walls_default`: `wall_*` が 4 個ちょうどである前提

これらは「box ジオメトリの一部 face」を検証する形に書き直す。具体的には:
- 「North エッジに対し `wall_north_inner` face が 1 個生成される」のように face type 命名規則を更新
- 厚みのあるジオメトリの inner / outer 面の z 座標を別々に検証

**マイグレーションは proposal/spec の archive 時に既存 spec が更新されることで完了する** (既存 scenario の更新)。

## Risks / Trade-offs

- **face 数増加 → 描画コスト**: 視界 13 セルとして face 数は概算で 4 倍程度 (壁 4 → 約 16-20 face/壁 + 柱 + トリム)。`ImmediateMesh` で毎フレームではなく「移動・回転時のみ」再構築するため、フレームレートへの影響は無視できる範囲と判断。  
  → Mitigation: パフォーマンス問題が出たら「コーナー柱は WALL 隣接のみ」「幅木 / 笠木は手前 N セルのみ」など段階的最適化が可能。
- **コーナー柱が視界を圧迫**: 0.25m 角の柱が部屋の四隅から少しはみ出すため、狭い廊下で視界が窮屈に感じる可能性。  
  → Mitigation: 通路の有効幅は 2.0 - 2 × (0.10 + 0.05) = 1.70m を確保 (壁 box + 柱はみ出し)。実装後にスクリーンショットで確認し、必要なら柱サイズを 0.22m に縮小する余地あり。
- **テスト書き換えコスト**: 既存の 4 テストがジオメトリ前提を持っているため修正必要。  
  → Mitigation: 新仕様に沿って書き直すだけで、テストカバレッジは維持される。
- **`cull_disabled` シェーダ設定の継続**: 厚み box になっても面の表裏は明確になるが、シェーダ側を `cull_back` に切り替えるとパフォーマンスは少し改善する。  
  → 今回はシェーダに触れないため `cull_disabled` のまま (将来の最適化候補)。
- **マップ境界の柱**: マップの最外周コーナーには WALL 扱いの仮想エッジしかないが、ルール通り柱を立てる。プレイヤーが見ることのある外周セル (start/goal 等) で角の柱が普通に見える形になる。意図通り。

## Migration Plan

1. **Step 1 (リファクタ、見た目変更なし)**: `build_meshes(visible_cells, wiz_map)` を新設、内部で従来通り `build_faces(cell, pos)` を呼んで結果を集約する。`DungeonScene._rebuild_mesh` を新 API へ切り替え。既存テストは全 pass のまま。
2. **Step 2 (壁の box 化)**: 壁エッジ生成を per-batch ループに移し、`_add_wall_box` を実装。既存 `_add_wall_face` を内部から削除。テストを box ジオメトリ前提に書き直し。
3. **Step 3 (コーナー柱)**: コーナー判定ヘルパ + `_add_pillar` 実装。新規テスト追加。
4. **Step 4 (幅木 / 笠木)**: 各 WALL/DOOR エッジに対し `_add_skirting` / `_add_cornice` を呼ぶ。新規テスト追加。
5. **Step 5 (ドア建具)**: DOOR エッジ生成を `_add_door_assembly` (lintel + jamb + panel) に置換。既存 `door_north` 等の単一クワッドは廃止。新規テスト追加。

各 step で commit。テストが通った状態で次の step へ進む TDD ワークフロー。

ロールバックは git revert で各 step 単位に戻せる。
